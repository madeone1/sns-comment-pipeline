# SNS Comments 클라우드 운영

2026-11-09 [선별·시트 연결 로컬 변경](WORKFLOW.md)을 준비했다. 실제 마스터 7개 탭의 초기 반영과 원문 대조는 완료했으나, 이 변경의 운영 배포·Google 무인 인증·Drive 연결은 미완료다. `workflow.enabled`는 다음 배포본의 동작 설정이며 현재 클라우드에 적용됐다는 뜻이 아니다.

중복 일일 업무 [자동 병합](DAILY_MERGE.md)을 2026-11-09 배포·활성화했다. 같은 날짜의 가장 이른 페이지를 유지하고 새 페이지 정보를 템플릿 항목별로 합친다. 하위 DB는 원본 객체·행·보기·ID를 유지해 이동하며, 사용자 허용에 따라 새 페이지의 토글 생성 버튼만 제외한다. `enabled=true`, `apply=true`, `preserve_child_databases=true`, `allow_template_toggle_buttons=true`다. 실제 템플릿 복사본의 본문·DB 보존, 실제 휴지통 이후 변경 시 복구, 재실행 중복 방지와 289개 테스트를 통과했다. 운영 주간 생성과의 실제 충돌 검증은 2026-11-16 이후 확인 대기다.

배포 이미지 `20261109-031829`, digest `sha256:4f02b55d3f36919da14cafbfcf4597bd12a470bc3e1238ebf6e2bede8457973c`. 기존 `sns-comments-daily`는 `--all-accounts`를 유지하며, 새 `notion-daily-merge`는 `--merge-only`로 SNS 수집·AI·개인 Notion OAuth 갱신 없이 병합만 수행한다. WSH Secret은 기존 실행 계정에 해당 Secret 하나의 읽기 권한으로 연결했다. 두 작업은 같은 전역 잠금을 사용한다. **매주 월요일 04:00 KST** 전용 실행과 기존 매일 08:00 SNS 수집 전 재확인을 사용한다. 사용자가 생성 시각의 변동을 고려해 04시로 지정했다.

실제 클라우드 실행 `notion-daily-merge-27twt`가 13:04 KST에 성공했다. 활성 apply 모드로 일일 업무 15개·단일 페이지 날짜 15개·중복 날짜 0개·병합 0개를 확인했다. 현재 운영 페이지는 변경하지 않았다. 단일 페이지에서는 본문·하위 DB 검사를 하지 않는다. 결과는 비공개 상태 저장소의 `daily-merge/2026-11-09/latest.json`과 로컬 `.local/recovery-2026-11-09/cloud-daily-merge-verification.json`, 실제 템플릿 보존 증거는 `native-merge-smoke-verification.json`에 있다. 미지원 내용·충돌·검증 실패는 원본을 유지하고 보류한다.

2026-11-09 운영 변경: 기존 `sns-comments-daily` 예약(매일 08:00, Asia/Seoul)을 유지하고 Cloud Run 인수를 `--all-accounts`로 설정했다. `cloud.scheduled_accounts`의 대표·부산·속초 세 계정을 순차 실행하며 계정별 DB와 보고 상태를 분리한다. 전역 잠금은 공유 OAuth 초기화와 세 계정의 Notion 호출 전체를 보호한다. 개별 계정 실패는 요약에 기록하고 다음 계정을 계속 실행한다. 전체 결과는 `pipeline/YYYY-MM-DD/status.json`에 보존한다.

사용자 결정: 주말·휴일 등 집계 날짜의 일일 업무가 없으면 원래 집계 날짜를 보존해 다음 존재하는 일일 업무에 날짜별로 기록한다. 아직 그 다음 업무일이 오지 않았으면 `pending`으로 대기하고 정상 수집과 보고 대기를 구분한다. 페이지 부재는 다른 계정의 수집이나 이전 게시물 별도 추적을 중단시키지 않는다. 중복 페이지·잘못된 응답·실제 쓰기 실패는 오류로 남기며 자동 페이지 생성은 하지 않는다.

조회 보완: 이벤트 날짜의 ISO 날짜 부분으로 비교하고 SQL 결과가 비면 구조화 날짜 필터로 재확인한다. 후보 페이지를 fetch해 유형·날짜·식별값을 확인하며, MCP의 UUID 또는 공식 페이지 URL 형태 식별값을 모두 검증한다. 과거 부산·속초 테스트 DB는 클라우드에 이관하지 않았고 새 수집 원본부터 계정별 비공개 경로에 보존한다.

실제 검증 완료: 이미지 `20261109-003819`, 실행 `sns-comments-daily-89zs2`가 2026-11-09 09:39:20~09:46:34 KST에 성공했다. 세 계정 모두 기본 수집·별도 추적 상태 `complete`, 보고 상태 `published`, 대기 보고 0건이다. 대표 계정은 최근 게시물 4개·기간 내 댓글/답글 51건이고 부산·속초는 최근 7일 게시물이 없어 각각 0개·0건이다. 이는 과거 게시물 전체에 새 댓글이 없다는 뜻이 아니다. 오늘 일일 업무에서 세 계정 보고 각 1개와 11/7·11/8 대표 계정 보류 보고 각 1개의 실제 반영을 확인했다. 체크포인트와 계정별 원본은 클라우드에 보존됐으며 다음 정기 실행은 11월 10일 08:00 KST다. 회귀 테스트 209건 통과. 증거: `.local/recovery-2026-11-09/three-account-verification.json`, `notion-three-account-verification.json`.

초기 배포 실행의 설정 읽기 오류는 로컬 계정 설정 파일의 `0600` 권한과 컨테이너 사용자 소유권 차이 때문이었다. Docker COPY에 실행 사용자 소유권을 명시해 해결하고 위 실제 실행으로 확인했다. 기존 조회 오류가 발생한 시점의 원응답은 보존돼 있지 않아 과거 원인을 단정하지 않으며, 현재 조회·형식 검증·빈 결과 재확인·주말 이월 처리와 실제 보고 성공을 검증했다.

## Notion 연결

기존 배포 구성은 공식 Notion MCP의 OAuth/PKCE와 동적 클라이언트 등록을 사용한다.

2026-11-06 로컬 소스에 **전달받은 MCP 토큰** 방식을 추가했다. `test-notion-token.command`로 숨김 입력 후 연결·필수 도구 권한·기존 보고 대상 조회를 검사한다. 토큰을 저장하지 않으며 결과만 `.local/notion-mcp-token-test.json`에 보관한다. 실제 문서 쓰기는 수행하지 않는다. [Notion 공식 안내](https://developers.notion.com/guides/mcp/get-started-with-mcp)에 따르면 MCP 토큰은 공식 엔드포인트에 Bearer 헤더로 보낸다. 일반 Notion REST API의 연결 토큰과 구분한다.

현재 Cloud Run은 `SNS_NOTION_MCP_TOKEN`을 운영 인증으로 사용하지 않는다. 이 변수가 있어도 진단용으로 무시하고 기존 `mcp_oauth` 연결과 Secret Manager의 갱신 경로만 유지한다. 별도 MCP 토큰 진단 도구의 존재를 운영 인증 전환으로 해석하지 않는다.

`connect-notion.command`는 최초 브라우저 승인용이며 예약 실행기가 아니다. 승인 결과는 우선 macOS 키체인에 저장하고, 배치 시 전용 Secret Manager로 옮긴다. 클라우드에서는 이 저장소를 읽어 자동 갱신하며, 갱신된 refresh token을 다시 비밀 저장소에 보존한다. 초기 연결 Mac의 키체인 값은 이후 클라우드 갱신과 동기화되지 않으므로, 재배포 때 초기 값을 덮어쓰지 않는다. 기존 Codex 플러그인의 인증정보를 추출하거나 재사용하지 않는다.

OAuth 권한은 승인한 Notion 사용자·워크스페이스에 따른다. 프로그램의 쓰기는 설정된 일일 업무 데이터베이스의 날짜가 일치하는 페이지, 그 안의 `SNS Comments` 자동 보고로 한정한다. 일일 업무의 다른 항목·하위 페이지·수동 기록은 보존한다. 같은 날짜 재실행은 자동 보고를 갱신한다. 보고가 없는 경우 기존 일일 업무를 임의로 새로 만들지 않는다.

## 수집과 보고

1. 분산 잠금을 획득한 후 OAuth를 초기화해 중복 수집·토큰 갱신 경쟁을 막는다.
2. 최신 규정집을 매번 읽고 버전과 수정 시각을 남긴다. 읽지 못하면 분석 완료로 표시하지 않는다.
3. 최근 7일 게시물과 같은 기간 댓글·답글만 기본 수집한다. 전체 과거 게시물은 순회하지 않는다. 확인된 이전 게시물 활동은 기본 보고를 기록한 뒤 별도 수집하며 본 집계에 합산하지 않는다. 같은 기간의 완료된 별도 추적은 재실행 시 재사용한다.
4. 원문 DB와 체크포인트를 Cloud Storage에 먼저 보존한다. AI 분류는 원문 해시·규정·모델 기준으로 별도 저장해 미처리분부터 이어간다.
5. AI 결과의 댓글 ID, 중복·누락, 분류 항목, 근거, 요약 3줄과 인사이트·실행안 최대 3개를 검증한다. 원문을 덮어쓰지 않는다.
